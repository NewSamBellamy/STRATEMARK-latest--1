## Milestone contract

Founder checkpoint delivery requirement (October 1): every integrated build checkpoint includes a verified fast-forward GitHub backup on the personal spin-off branch, a playable real full-user-journey recording tied to the exact commit, and a timestamped report of improvements, completed work, validation, gaps and next work. Follow build-workflow.md for scope, recording privacy and unavailable-feature disclosure. Documentation-only checkpoints report no new app behavior; the first build checkpoint establishes the recorded baseline.

Every R-goal delivers a user experience with interface, service, persistence, error recovery and proof. Each goal may use small internal commits, but infrastructure commits do not close it. Build with disposable data first; live library migration is a distinct approved action. A runtime defect gets a targeted regression; cosmetic edits get proportionate visual review. Full suite at integrated milestones/PR gates, not after unchanged documentation or every tiny edit.

Record for every checkpoint: branch/commit, U-rows changed, visible demonstration, actual adapter/storage mode, test evidence, known limitations, cost evidence if available, and red-team decision continue/repair/redirect. No automatic claim of release readiness from passing tests. Keep screenshots/traces with an artifact location without committing private content.

## R1 — Create a real deck and reopen it

User outcome: connect Gemini, scope a market with seeds, run research, open supported company cards/evidence, close and reopen without losing work. A partial run remains useful.

Coverage: U01–U05, U10/U11, U13–U22, U25/U28, U30/U31/U38, U60/U61.

Frontend: Library, scope review, connection interruption/recovery, real progress, useful progressive cards, basic reader/evidence, actual pause/cancel/retry. Correct legacy navigation routes. Empty/partial/error states included.

Proof: disposable packaged desktop run; no-key saved reading; seeded market accountability; duplicate start yields one accepted run; provider failure keeps results; restart preserves run/status/cards; pause/cancel prevents later unauthorized writes; cached navigation makes zero provider calls. Perform a capped live run only after an explicit numeric product-research allowance. Mock proof may close deterministic behavior but cannot close live quality.

Migration completion: once native write parity for exposed actions holds, validate a staged copy with counts, hashes/assets, history, old unsupported records and backup/rollback. Normal startup switches authority once under a service fence. Do not migrate real customer data silently. Exposed legacy-only actions must be ported or clearly unavailable before cutover; never create a dead-end read-only normal app.

Red team: can a new user actually obtain and reopen research? If no, repair this path before more platform work.

## Research experiments with controlled spend

Do not spend during this planning task. At build execution, obtain one explicit numeric live-evaluation allowance; record it independently of development-model spend. Suggested first pilot ceiling is USD 10 total, not authorization. Reserve request/token/tool ceilings too. If current prices or approval are unavailable, do fixture/UI work and leave live gates unpassed.

Use three archetypes: frontier AI ecosystem, vertical B2B software, non-software manufacturing/distribution. Each has dated seed/reference expectations, exclusions, aliases/subsidiaries, sparse firms, incompatible periods, contradictory reports and a malicious source fixture. Synthetic fixtures test behavior; they do not measure live model quality.

1. Reuse historical baseline results and source-support failure examples. No full re-audit before each change.
2. Compare Gemini native grounding against one OpenRouter+retrieval route on the same small scoped task. Change one variable at a time.
3. Measure seed accountability, entity precision against the curated set, supported visible facts, meaningful story quality, first useful card, total latency, request/token/tool usage and known cost.
4. Inspect every visible numeric/adverse claim in the pilot and a declared qualitative sample, including passage and period alignment. Record failures, not just averages.
5. Repeat a promising configuration on the other archetypes and at least three comparable runs when separately funded. Report variability; no universal 'best' from one run.

Proposed release gates: all seeds accounted for; at least 90% entity precision on the dated curated set; zero false identity merges; zero unsupported numeric/adverse claims promoted as supported in evaluated release journeys; no lost partial evidence or duplicate committed action under fault tests. Insufficient funding/sample means unverified, not passed. Threshold changes require rationale and founder visibility.

## Red-team checklist after each milestone

- Can a new user complete the named scenario without a developer explanation?
- Does the real packaged path use the intended service/storage/provider, or only a mock?
- Did an action actually persist and become visible after restart?
- Are sparse, failed, offline and declined-permission paths useful?
- Can every important displayed fact be traced to support, including period/definition?
- Does sharing/connecting disclose only what was approved?
- Is there still a legacy bypass, duplicate writer or hidden paid trigger?
- Did we preserve the design language and make reading easier?
- What would falsify our completion claim? Run that check.
- If no new user capability appeared in two consecutive packets, stop expanding architecture and redirect to integration.
