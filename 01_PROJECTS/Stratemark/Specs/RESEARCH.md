# Research and decision evidence

Checked September 30, 2026. Plan version: 1.0.0.

This ledger separates documentation facts, repository observations, and our recommended design. Official documentation is not a benchmark of Stratemark's current behavior. Astra performed a read-only architecture red team; the coordinating agent inspected the code and primary sources. No live provider research, paid quality comparison, security certification, or packaged installer verification was performed for this document.

Agent-Reach's configured search backend was unavailable; official-source web search/open was used instead. No tool installation or provider key reuse was needed. Dates are inspection dates, not a guarantee of future API compatibility.

## 1. Primary source ledger

| ID  | Primary source                                                                                                            | Supported fact / design implication                                                                                                                                                                                                                                              |
| --- | ------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| S01 | [SQLite: appropriate uses](https://sqlite.org/whentouse.html)                                                             | SQLite suits local application storage. Our choice of one authoritative vault is a design inference, not SQLite prescribing this exact product layout.                                                                                                                           |
| S02 | [SQLite WAL](https://sqlite.org/wal.html)                                                                                 | WAL readers and a writer coordinate on the same host; it is unsuitable for network-filesystem sharing. Use a local live vault and explicit portable snapshots.                                                                                                                   |
| S03 | [SQLite online backup](https://sqlite.org/backup.html)                                                                    | A consistent live backup requires the appropriate backup mechanism. Copying only the main database while WAL is active is not the planned backup strategy.                                                                                                                       |
| S04 | [SQLite FTS5](https://sqlite.org/fts5.html)                                                                               | Indexed full-text search is available. Choose lexical local search first. Retention/deletion requires explicit treatment; do not promise forensic erasure of old indexes/backups.                                                                                                |
| S05 | [OpenCode permissions](https://opencode.ai/docs/permissions/)                                                             | Action permissions can distinguish allowed, ask, and denied operations. Adopt this clarity, not another product's permissive defaults.                                                                                                                                           |
| S06 | [OpenCode agents](https://opencode.ai/docs/agents/)                                                                       | Role-specific agents, tools, and step limits support bounded delegation. We implement roles over saved tasks, not endless processes.                                                                                                                                             |
| S07 | [OpenCode providers](https://opencode.ai/docs/providers/)                                                                 | Broad provider and local/custom endpoint access is possible; protocol families and capabilities differ. Stratemark must verify each route rather than claiming all OpenAI-compatible endpoints are identical.                                                                    |
| S08 | [Anthropic: building effective agents](https://www.anthropic.com/engineering/building-effective-agents)                   | Start with simple workflows and add agent complexity where it earns value; orchestration increases latency and cost. This supports measured Sentinel/Scout delegation, not mandatory multi-agent debate.                                                                         |
| S09 | [Gemini Google Search grounding](https://ai.google.dev/gemini-api/docs/google-search)                                     | Native grounding provides search and citation metadata. Normalize actual response shapes and satisfy the applicable display/service requirements at implementation; do not assume raw citations alone prove support.                                                             |
| S10 | [OpenRouter web search](https://openrouter.ai/docs/guides/features/plugins/web-search)                                    | Search is explicitly enabled and can have additional costs. A generic OpenRouter chat request is not automatically a retrieval pipeline; native search can be another tested capability path.                                                                                    |
| S11 | [Firecrawl search](https://docs.firecrawl.dev/features/search)                                                            | Search can be combined with page-content retrieval. Selective search-then-retrieve is our cost/quality candidate, not a documented guarantee of best results.                                                                                                                    |
| S12 | [Perplexity Search API](https://docs.perplexity.ai/docs/search/quickstart)                                                | Search returns ranked results and content metadata. Keep raw search separate from generated answers and distinguish publication, update, event, and retrieval dates.                                                                                                             |
| S13 | [Electron security](https://www.electronjs.org/docs/latest/tutorial/security)                                             | Isolation, sandboxing, safe navigation, and IPC sender validation matter for untrusted content. Keep source pages outside privileged application capabilities.                                                                                                                   |
| S14 | [Electron safeStorage](https://www.electronjs.org/docs/latest/api/safe-storage)                                           | Protection uses OS facilities and differs by platform. Windows protection does not isolate secrets from every process under the same user; Linux can have an insecure fallback. It does not encrypt the research vault.                                                          |
| S15 | [Electron code signing](https://www.electronjs.org/docs/latest/tutorial/code-signing)                                     | Signing is part of desktop distribution. Actual certificates, signing configuration, and packaged tests remain a production gate, not planning accomplishments.                                                                                                                  |
| S16 | [MCP versioning, 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning)                   | Current protocol and older clients have different lifecycle/version semantics. Pin and test compatibility rather than implementing an assumed legacy-only handshake. This page was available earlier in research; one later re-open returned an access error. Revalidate at G07. |
| S17 | [MCP transports](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports)                               | Stdio and Streamable HTTP provide standard transport paths. Transport support does not imply every named host supports our server or tool schemas.                                                                                                                               |
| S18 | [MCP tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)                                        | Tools have structured schemas/results and require validation/access control. Tool annotations are not authentication. Use stable job handles for durable asynchronous work.                                                                                                      |
| S19 | [MCP Streamable HTTP](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http)          | Local servers should bind localhost, validate Origin, and authenticate. New transport behavior differs from older versions; a local listener is not automatically safe or remotely reachable.                                                                                    |
| S20 | [MCP security best practices](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices) | Token audience validation, avoiding token passthrough, and SSRF protections matter. A connection grant must be enforced server-side through all linked records and egress.                                                                                                       |
| S21 | [OpenAI: extending with MCP](https://learn.chatgpt.com/docs/extend/mcp)                                                   | Local Codex/desktop and hosted surfaces have different connection paths. A cloud service does not read a user's local configuration or localhost merely because an MCP server exists.                                                                                            |
| S22 | [OpenAI Secure MCP Tunnel](https://developers.openai.com/api/docs/guides/secure-mcp-tunnels)                              | An outbound private connection can bridge a private server to supported OpenAI surfaces with required account permissions. It does not provide public plugin distribution; selected data still traverses the remote service.                                                     |
| S23 | [OpenAI MCP server guide](https://developers.openai.com/plugins/build/mcp-server)                                         | Host tool/schema, citation, and inspection requirements must be met. Standard search/fetch wrappers and public submission are compatibility work, not implied by exposing custom tools.                                                                                          |
| S24 | [W3C: animation from interactions](https://www.w3.org/WAI/WCAG22/Understanding/animation-from-interactions.html)          | Nonessential interaction-triggered motion should be disableable. | S25 | [Node SQLite API](https://nodejs.org/api/sqlite.html)                                                                     | The built-in API is version-dependent and the opened current documentation labels it release-candidate stability. | S26 | [Serper official service](https://serper.dev/)                                                                            | Serper exposes search result data. Sources are linked to actual documents, not search results. Do not copy large passages or private provider responses into this ledger. Architecture recommendations and operating thresholds are our choices unless explicitly attributed as facts.

Before a phase consumes external API/SDK details, re-open the relevant documentation and record endpoint, SDK/runtime version, response fixture date, capability test, and pricing timestamp. Provider/model/pricing/host compatibility claims should be revalidated at every live evaluation and release gate, even if this document is recent. For relatively stable architecture guidance, recheck if more than 90 days old or if the dependency changes. Unavailable evidence remains unverified; do not silently fill the gap from memory.

## 2. Decisions selected from the open questions

| Question                                 | Decision and rejected alternative                                                                                                                                  | Verification that can change it                                                                          |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------- |
| What should users accomplish first?      | A bounded useful deck and one deep company dossier, not a finished-looking exhaustive report.                                                                      | G03/G04 first-session walkthrough and time-to-first-useful-card.                                         |
| How do agents feel alive?                | Real tasks, saved memory, meaningful changes, and recoverable work; reject animated fictional activity.                                                            | G02 event/task parity and G06 offline/restart tests.                                                     |
| Do Scouts run continuously?              | Persistent dossiers with a bounded worker pool; reject a live model process per company.                                                                           | Cost/concurrency/recovery experiments.                                                                   |
| What owns researched data?               | Local transactional vault plus source assets; reject cloud-required storage and browser localStorage as production authority.                                      | G01 migration/backup/recovery and offline reads.                                                         |
| How should companies fit multiple decks? | Canonical immutable identity with many-to-many memberships and market roles; reject permanent single-market assignment.                                            | Identity/alias/parent and two-market fixtures.                                                           |
| What should a card show?                 | Identity, purpose, market role, and a few supported relevant facts; reject generic scores and decorative card backs.                                               | Visual review and metric-support/comparability fixtures.                                                 |
| How should ranking work?                 | Explain goal relevance; offer valid quantitative sorts and explicit comparisons; reject universal company power ranking.                                           | G04/G05 scope/metric profile tests.                                                                      |
| What belongs in Culture/Vice/B2E?        | Workplace/community findings, attributed Risks, and Barriers to entry. Findings remain separate from financial metrics.                                            | Category-specific quality fixtures and founder usefulness review.                                        |
| What reports do we create?               | Written evidence-linked briefs from fixed input revisions; defer speculative white papers.                                                                         | Citation/unknown/report input-version tests.                                                             |
| Which provider setup is best?            | Simple existing Gemini native route, flexible model + explicit retrieval route; retain broader tested endpoints. No live winner claimed.                           | E02-E04 evidence, cost, latency, and repeated quality comparisons.                                       |
| How do monitoring and spending work?     | Opt-in daily local checks under explicit caps; reject autonomous unlimited budgets and implied coverage while closed.                                              | Fake-clock, cost reservation, duplicate update and revoke tests.                                         |
| What can an assistant do?                | Scoped cached reads first, then approved shared-service jobs; reject arbitrary filesystem/SQL/shell/key access.                                                    | G07 scope/identity/injection/replay/host compatibility tests.                                            |
| How do hosted agents reach local data?   | Optional tested private connection route later; no default public relay or hidden cloud copy.                                                                      | Actual host permissions/transport/egress validation. Muse/Dots documentation and tests are still needed. |
| How do we avoid context rot?             | Canonical spec, stable IDs, cold-start state, versioned decisions, bounded packets and actual completion evidence. Reject chat-only memory or duplicated roadmaps. | Doc linkage/ID checks and a fresh-agent cold-start exercise.                                             |

Defaults are intentionally revisable by evidence and human direction, but not by silent executor preference. Benchmarks decide routing; they do not loosen integrity gates.

## 4. Known uncertainties, handled without hallucinating

- Best model/retrieval combination: not established. Run bounded experiments before naming a measured winner.
- Exact provider prices and credits: not fetched as an execution budget. Read current pricing and reserve limits when an approved live experiment begins.
- SQLite binding inside this packaged Electron version: not tested. G01 spike decides the dependency; local transactional architecture is already chosen.
- Muse/Dots host transport, authentication, and UX contracts: not supplied or tested. Build a standard local bridge, then inspect actual host documentation and test rather than invent compatibility.
- Future MCP/host/SDK behavior: volatile; pin and test a real support matrix at G07.
- Production signing, installer behavior, license/dependency/content-service compliance: release gates, not accomplished by this plan.
- Absolute hallucination prevention: impossible to guarantee. Use fail-closed support checks, explicit uncertainty, human review, and measured failure reporting.
- At-rest research encryption: not implemented/planned for v1. State local plaintext ownership clearly; optional encryption is a separate future design.

These are concrete verification tasks, not unresolved product choices sent back to the founder. Missing externally required access or production authority remains a real boundary; research cannot grant it.
